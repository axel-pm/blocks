Swap where your AI runs — without touching your app

The safety check, in plain terms: a target is only used if it really exists, has its access key, and has been approved for production. Anything else is quietly swapped for the vetted default.
🛟
Never routes somewhere you didn't approve. A typo, a missing key, or an un‑vetted provider can't send your users' traffic to the wrong place — it falls back to the trusted default, or refuses rather than send an unauthenticated request.

rag

Answer from your own documents — with citations

Point it at a folder of documents. It turns them into a searchable index, then for any question it pulls the most relevant passages and hands them over with their source, so the answer can be checked.

🔒
Doesn't leak your secrets. The folder reader skips passwords, keys and credential files by name and by content, skips huge/binary files, and caps how much it reads. Passages are "fenced" so text inside a document can't issue instructions to the model.

Can never cry "verified" by mistake. If the checker fails or replies in a form it doesn't understand, the result is always "not verified" — never a false pass. A broken checker won't crash answering.
blocks · guardrails
guardrails

Three safety tools for an AI app

Use any one on its own — they share no dependencies. Keep personal data out of the model, stop runaway spending, and stop text from smuggling in instructions.

🔒 Hide personal data

Swaps emails, phone numbers and names for placeholders before text goes to the model or the logs — and can put the originals back in the reply.

jo@acme.com → ⟦EMAIL_1⟧

💳 Cap spending

A per‑user limit over a time window. When counting races, it over‑counts rather than over‑admits — the safe direction for a budget.

over $5 today → blocked

🚧 Fence untrusted text

Wraps a document so the model treats it as data, not commands — a pasted "ignore your rules" can't break out.

+ an advisory "looks injected?" check
🛟
Best‑effort safety, zero dependencies. These reduce risk and never make it worse; they're one layer of defence, not the only one. Placeholders carry a per‑call random tag so they can't be guessed and abused.

settings

Change how the app behaves — live, no redeploy

An operator flips a setting and it takes effect right away. When the app needs a setting's value, it checks three places in order and uses the first good one.

1
An environment override set?
checked first, takes effect instantly — handy for emergencies
↓ if not
2
A stored value (saved by an operator)?
lives in your database; changing it takes effect without a redeploy
↓ if not
3
The built‑in default
always present, so there's always an answer
A short in‑memory cache keeps this fast; saving a new value refreshes it immediately.
🛟
A bad value can't break you. A stored or env value that doesn't make sense is ignored in favour of the default (and logged), so a typo in config never takes down your live app.
